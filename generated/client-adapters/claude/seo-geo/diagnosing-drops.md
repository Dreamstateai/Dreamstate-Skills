# Diagnosing a traffic or visibility drop

## Procedure
1. Establish which surface dropped before proposing anything: classic organic (Search Console clicks/impressions/rank via `visibility.keywords_get` and `integrations.gsc.search_analytics_get`), AI citation share (`visibility.prompt_metrics_list`, `visibility.probe.runs_list` for the trend, `visibility.overview`), or AI referral traffic (`visibility.ai_traffic`). These move independently; a GEO drop with flat classic rank, or the reverse, is a normal and common pattern, not a data error.
2. Pull the comparator period alongside the current one. `visibility.keywords_get`'s `prev_*` fields and `search_analytics_get` date ranges give this for classic SEO; `probe.runs_list`/`prompt_metrics_list.last_run_at` give it for GEO, by comparing the two most recent batches for the same tracked prompt. A single-period number is not a drop, it is a snapshot; state `insufficient_evidence` if no prior comparator exists yet.
3. Check for a measurement-side cause before a content-side one: `integrations.gsc.status` (did the connection lapse), `seo.robots_audit` and `visibility.html_analysis_get` (did a crawler get newly blocked), `seo.agent_readiness_latest` (did llms.txt or agent readiness regress). A blocked crawler or lapsed connection produces a drop that looks identical to a real ranking or citation loss but has a completely different fix.
4. If the surface is technical (page broke, crawler blocked, Core Web Vitals regressed), name the specific failing check and its `visibility.html_analysis_get` / `visibility.pagespeed_get` evidence. If the surface is content (a competitor now ranks or is cited for the query), name the competing URL from `visibility.citations` or `search_analytics_get` and whether the gap is coverage (no page exists) or quality (a page exists but underperforms).
5. If the request names a specific query and the cause is unclear from evidence already read, ask the one consolidated question that would resolve it (for example, whether a recent page change or migration coincides with the drop window) rather than guessing.

## Reporting shape
Close a drop investigation with the same five completion fields the rest of this skill uses: `observation_state` (what was actually observed, with the two compared periods and their dates), `evidence_state` (disclosed evidence and its cohort/sample bounds, or `insufficient_evidence` if no comparator exists), `plan_state` (the prioritized fix, ranked by evidence strength, or `not_applicable` if this was read-only diagnosis), `approval_state` (whether any write capability was proposed and its status), `run_state` (`terminal` if a proposed fix's capability call has finished, `not_applicable` for a diagnosis-only turn). Never state a cause without the capability read that supports it named alongside the claim.

## Traps
- Diagnosing a GEO citation drop using only `visibility.overview`: the aggregate can look flat while one or two heavily-weighted tracked prompts lost citations entirely; always drop into `prompt_metrics_list` per-prompt numbers.
- Blaming "AI search cannibalization" for a classic-SEO click drop without checking `integrations.gsc.status` and `seo.robots_audit` first; a lapsed GSC connection or a newly blocked crawler produces the same symptom and is a five-minute fix instead of a content rewrite.
- Proposing a content rewrite before checking whether the drop is even real, i.e. before pulling the comparator period.
